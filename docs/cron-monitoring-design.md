# Cron job monitoring — design (APPROVED 2026-10-11, built, not yet committed/deployed)

Status: approved 2026-10-11; implemented in `scripts/cron_watch.py` (tests: `tests/test_cron_watch.py`).

Implementation deviations from the text below:
- Alert de-duplication lives in the state file (`state["sent"]`), not Redis, so the watcher works when Redis is down.
- Silence is measured from the log file's mtime (no size tracking needed); history stores the longest silence
  observed at 15-min checks during each run.
- The watcher is called at the top of `log_monitor.main()` (before the early-return paths), via `cron_watch.run_safe`.
- Missing-wrapper alert fires immediately (not only when a slot is due).
- A watcher crash emails once per re-alert window (flag file `data/cron_watch_error.flag`).

## 1. Why this exists (the incident)

From about 2026-08-05 to 2026-10-10 all 11 wrapper scripts (`/home/opc/mail/run_*.sh`, generated by
`setup_cron.sh`, untracked in git) were missing on the VM. Cron kept firing and logged
`No such file or directory` to `/var/log/cron`, but nothing read that file, so for about two months
there was no digest email, no nightly DB backup (last dump 2026-08-05), no forms sync, no outreach and no
weekly summary. Every other component (systemd workers, scheduler, `log_monitor.py`) kept running and
reported nothing wrong, because the failure happened before any Python started. Root cause of the deletion
was never found. This design makes that class of failure loud, whatever its cause.

## 2. Goals and non-goals

Goals
1. Alert when a scheduled cron job did not start at its slot (missing wrapper, cron down, VM asleep).
2. Alert when a job started but stopped making progress, or ran far longer than it normally does.
3. Alert when a job finished with a non-zero exit.
4. No registration step: a new cron line is monitored automatically. A line the monitor cannot understand
   raises an "unmonitored cron job" alert instead of being skipped.
5. No hardcoded numbers: every threshold is a `config.py` value read from an env var.

Non-goals
- Replacing the existing error scanning in `scripts/log_monitor.py`.
- Monitoring systemd services (the watchdog and manager already cover them).
- Monitoring the correctness of a job's output (only "ran", "progressing", "exit code").

## 3. Where it lives

A new module `scripts/cron_watch.py` holding pure, testable functions, called once per run from
`log_monitor.main()` after the existing scan. It reuses `log_monitor`'s lock (`data/log_monitor.lock`),
its `_send_email()` (Gmail, same recipient) and its 15-minute cron entry. No new cron entry is needed, which
matters: a new cron entry could itself vanish.

New state file `data/cron_watch_state.json` (atomic write via tmp + rename, same pattern as
`log_monitor_state.json`). Alert de-duplication keys go in Redis (`cron_watch:alert:*`), like the existing
fingerprints; if Redis is down, fall back to the state file so an outage cannot hide a cron failure.

New dependency: `croniter` (pinned in `requirements.txt`). To verify before building: the deploy workflow
installs `requirements.txt` on the VM, so the dependency arrives with the next deploy.

## 4. How the schedule is derived (no config table)

Every run of the watcher does this:

1. `crontab -l` as the current user. If the command fails, or the crontab contains no pipeline lines,
   that itself is an alert ("crontab unreadable / empty"); an empty crontab means every job is silently off.
2. Walk the lines. Skip comments and blanks. A `NAME=value` line sets an environment value; `CRON_TZ=` sets the
   timezone for the lines after it (the live crontab uses `America/New_York`).
3. Split each job line into the five time fields and the command.
4. Resolve the log file the job writes to:
   - Wrapper style: the command is an executable under the project dir ending in `.sh`. Read that file and
     match its `LOG_FILE="$LOG_DIR/<prefix>_$(date +<fmt>).log"` line. Expand `<fmt>` with `strftime` for the
     slot date (so both `%Y-%m-%d` and `%Y-%m` logs work).
   - Direct style: the command contains `>> <path>`; expand `$(date +...)` and unescape cron's `\%`.
   - If the wrapper file does not exist, the log cannot be resolved by reading it; fall back to the wrapper's
     filename (`run_monitor.sh`) for the alert text. This is the exact incident case: the start check below
     fails and the alert names the missing file.
5. Compute due slots with `croniter` in the line's timezone (DST-safe) for the last `CRON_WATCH_LOOKBACK_HOURS`
   (default 24), ignoring slots that are newer than the start grace, and slots before the watcher first ran
   (`state.initialized_at`) so a first run after deploy does not produce a backlog storm.
6. A line that cannot be resolved to a log (neither wrapper nor `>>`) and does not match an ignore pattern raises
   one "unmonitored cron job: <line>" alert per day until it is fixed or ignored on purpose. This is the safety
   net that stops a new job being silently skipped.

Ignore list (the only config the monitor needs, `CRON_WATCH_IGNORE_PATTERNS`, comma-separated regexes):
- the keep-alive hash loop (no log),
- `scripts/log_monitor.py` (cannot watch itself, see section 9),
- the 9 AM fallback line (starts with `grep -q`, only runs when the 7 AM run failed; the 7 AM slot already
  covers it).

## 5. Checks per run

All checks read logs and state only; none of them execute jobs.

### 5.1 Start check (did it fire?)
For each due slot, look in the resolved log for a `[CRON] ... started at YYYY-MM-DD HH:MM:SS` line whose
timestamp is within `[slot, slot + CRON_WATCH_START_GRACE_MIN]` (default 10 minutes). The wrapper writes this
line as its first action, so its presence proves cron launched it, and its absence covers: missing wrapper,
cron daemon down, VM suspended, bad permissions. Matching by timestamp (not "any new line") means a manual run
or the 9 AM fallback cannot mask a missed 7 AM slot. Direct-style lines have no marker, so for them the check
is "file modified at or after the slot".

Alert text: `Cron job did not start: <wrapper or command> (slot 07:00, log monitor_2026-10-10.log not written)`.

### 5.2 Progress check (is it still working?)
A run is "in progress" if its log has a `started` line with no later `finished` line. Every watcher run
(every 15 minutes) records, per in-progress run, the log file size and the time it last grew
(`last_growth_ts`) and the longest silence seen so far in that run.

A run is stalled when its current silence exceeds
`max(CRON_WATCH_STALL_FLOOR_MIN, CRON_WATCH_STALL_MULTIPLIER x learned_max_silence)`
where `learned_max_silence` is the longest silence seen during that job's last
`CRON_WATCH_HISTORY_DAYS` days of runs that finished with exit 0. So a short job (DB backup) gets a tight
window and a quiet long job (heavy enrichment) gets a long one, with no per-job configuration.

A run is a runaway when its elapsed time exceeds `CRON_WATCH_RUNTIME_MULTIPLIER x` the longest recent
successful runtime, even if it keeps logging.

Learning period: a job with fewer than `CRON_WATCH_MIN_HISTORY_RUNS` (default 3) completed runs has no
learned baseline. It is judged on the floor only and the alert says "no history yet, default window used", so a
brand-new quiet job produces a soft, clearly labelled alert rather than a false alarm.

Resolution is 15 minutes (the monitor's cadence), so the floor must be at least two cycles (30 minutes).

### 5.3 Finish check (did it succeed?)
When a `finished at ... | exit=N` line appears for a run not yet recorded: `N == 0` records the run (duration and
max silence) into history; `N != 0` raises `Cron job failed: <job> exit=N`, once per run.

Note the existing `FLAG_PATTERNS` in `log_monitor.py` already matches `[CRON] ... | exit=<non-zero>`, but its
alerts are fingerprint-deduplicated for 7 days, so a job that fails every night would alert once and then go
quiet. Decision 10.3 below covers the overlap.

### 5.4 Crontab sanity
Alert if `crontab -l` fails, returns nothing, or the set of resolved jobs shrinks versus the previous run
(a line removed by accident).

## 6. State layout (`data/cron_watch_state.json`)

```json
{
  "initialized_at": 1760000000.0,
  "jobs": {
    "monitor": {                       // key = resolved log prefix
      "wrapper": "/home/opc/mail/run_monitor.sh",
      "history": [                     // last CRON_WATCH_HISTORY_DAYS days, successful runs only
        {"start": 1760000100.0, "duration_s": 316, "max_silence_s": 40}
      ],
      "current": {                     // the in-progress run, if any
        "start": 1760000100.0, "size": 18234, "last_growth_ts": 1760000900.0, "max_silence_s": 40
      },
      "recorded_starts": [1760000100.0]  // finished runs already processed
    }
  },
  "known_job_keys": ["monitor", "sync", "nightly"]
}
```

## 7. Alert delivery and de-duplication

- One email per watcher run, batching all new alerts (so a recovery from a multi-job outage does not send
  eleven mails). Subject: `[Cron Alert] N problem(s): <job>, <job> ...`.
- Alert key: `<kind>:<job>:<slot-or-run-start>`. Each key alerts once, then re-alerts every
  `CRON_WATCH_REALERT_HOURS` (default 24) while the condition persists, and clears itself when it recovers.
- A stall alert clears when the log grows again or the run finishes.
- If sending fails, the key is not marked as sent, so the next run retries (same rule as the current
  transient-SMTP handling).

## 8. Configuration (all in `config.py`, env-overridable)

| Name | Default | Meaning |
|---|---|---|
| `CRON_WATCH_ENABLED` | true | master switch |
| `CRON_WATCH_LOOKBACK_HOURS` | 24 | how far back to look for missed slots |
| `CRON_WATCH_START_GRACE_MIN` | 10 | window after a slot for the `started` line |
| `CRON_WATCH_STALL_FLOOR_MIN` | 30 | minimum silence before "stalled" (>= 2 monitor cycles) |
| `CRON_WATCH_STALL_MULTIPLIER` | 2 | stall window = this x longest healthy silence |
| `CRON_WATCH_RUNTIME_MULTIPLIER` | 3 | runaway = this x longest healthy runtime |
| `CRON_WATCH_MIN_HISTORY_RUNS` | 3 | runs needed before the learned baseline is trusted |
| `CRON_WATCH_HISTORY_DAYS` | 14 | history kept (matches log retention) |
| `CRON_WATCH_REALERT_HOURS` | 24 | re-alert interval while a problem persists |
| `CRON_WATCH_IGNORE_PATTERNS` | keep-alive, log_monitor, `grep -q` fallback | regexes of cron lines to skip |

## 9. Known limits

- If `log_monitor.py` itself stops (it is cron-driven too), nothing alerts. Partial mitigation: its 3-day digest
  email stops arriving, which is visible but slow. A stronger answer is an independent dead-man's switch (decision 10.4).
- A job that is silent while healthy for longer than its window will false-alarm until history teaches it; the
  learning-period wording and the floor setting limit this.
- Slots missed while the VM is deliberately off (maintenance) will alert once; acceptable.
- Direct-style cron lines (no wrapper) get only the weaker "file modified since slot" start check.
- The check proves the job started, progressed and exited 0. It does not prove the job did the right thing.

## 10. Open decisions for the user

1. Approve the approach as written (derive from crontab + wrappers, learned per-job stall window, ignore list).
2. Floor and multipliers: defaults above (30 min floor, 2x silence, 3x runtime) fine, or different?
3. Exit-code overlap: the existing `[CRON] ... exit=N` pattern in `log_monitor.py` already alerts once per 7 days
   per fingerprint. Recommendation: keep it for the error digest, and let `cron_watch` own per-run failure alerts
   (one per failed run). Alternative: suppress the old pattern to avoid two emails for one failure.
4. Independent dead-man's switch for `log_monitor.py` itself (e.g. an external heartbeat service, or a systemd
   timer that emails if `data/cron_watch_state.json` is older than N hours). Needs a separate approval since it
   involves an outside service or a new unit file; default is to leave this out of the first version.
5. Add the deploy-time self-heal (`deploy.sh` reruns `setup_cron.sh` when a wrapper listed in the crontab is
   missing)? Independent of this monitor; proposed as a separate small change.

### Agreed so far (2026-10-11)
- 10.3: keep both. The old `exit=N` pattern stays for the error digest; `cron_watch` owns per-run failure alerts.
- 10.5: narrow self-heal approved. `deploy.sh` reruns `setup_cron.sh` ONLY when a `run_*.sh` named in the crontab is
  missing or not executable, logs a loud line when it fires, and never touches non-pipeline crontab entries.
  Separate commit from the monitor.
- Still open: 10.1 (overall approval), 10.2 (thresholds), 10.4 (dead-man's switch, default: out of v1).

## 11. Build plan (after approval)

2. `scripts/cron_watch.py`: crontab parser, log resolver, slot computation, the four checks, state load/save,

3. Wire into `log_monitor.main()`; keep it from raising into the existing scan path (own try/except that logs and
   continues, but a failure of the watcher itself must email once).

   log-prefix resolution (daily and monthly), missed-start, manual-run-does-not-mask, stall learned vs floor,

   and confirming exactly one alert arrives, then restoring it.
